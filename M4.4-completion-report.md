## RPC và revalidation

- `apply.create.v1` nhận đúng `previewId`, `planDigest`, `viewNonce`, `operationId` và literal `approval: "create_only_v1"`. `apply.status.v1` nhận `operationId`. Cả hai dùng strict schemas. Operation ID từ 128 đến 256 bit dưới dạng hex lowercase. Không nhận target, paths, bytes, host ID hoặc fault controls qua Apply. [Wire schemas](shared/apply.ts)
- Receipt lấy từ immutable store của chính instance đã phát Preview v2, kiểm monotonic expiry, binding, digest và host ID truy vấn từ daemon. SDK handler context chỉ có `paseo`. Hai callers cùng host/installation có thể truy cập operation khi biết ID. Status kiểm host và installation slot do fixture plugin cấu hình. Slot đó ổn định qua restart để tra journal. Receipt mới vẫn cần instance và epoch hiện tại.
- Conflict, blocked hoặc observations không xác minh được dừng trước target writes. Dưới lock, sau durable claim, daemon chạy lại Preview v2 trong store riêng với cùng intent. Nó đối chiếu digest sau khi chuẩn hóa hai trường instance/epoch của lượt đối chiếu. Phép so này bao phủ saved settings revision/ref, nguồn và pinned SHA, plan, read-set, directory effects, và Kiro proof. Native preflight kiểm lại filesystem từ directory handles sau ACK. Writer nhận bytes đã giữ từ receipt gốc. [Orchestration](server/fixture-apply.ts)

## Lock, journal và crash semantics

Lock là stable `$PASEO_HOME/runtime/project-skills-m44/writer.lock` mode `0600` trong private fixture namespace mode `0700`, ngoài target. Native helper giữ `flock(LOCK_EX | LOCK_NB)` xuyên admission, receipt claim, preflight, writes và terminal settlement. Busy trước claim không consume receipt và không tạo operation. Một instance giữ reservation đồng bộ trước các await để chặn executor thứ hai. Hai subprocess cùng daemon tranh cùng lock inode.

1. Helper gửi `ready_to_admit` khi đã lấy lock. Journal gộp admission và receipt claim trong một record. Daemon ghi file private, fsync, publish exclusive qua hard link, rồi fsync directory. Sau revalidation thành công, daemon gửi `ADMIT`. Sai scope, journal lỗi hoặc stale đều không nhận ACK cho phép ghi.
2. Trước mỗi `mkdirat` hoặc `openat` exclusive, helper chờ `RECORDED` của mutation intent và kiểm lại linkage. Intent đã lưu đánh dấu row là `ownership_unknown`. Verified file/directory progress cũng chờ `RECORDED`. Do đó crash sau syscall nhưng trước verified progress để lại ownership chưa xác minh. Mỗi update dùng file mới đã fsync, atomic replace và directory fsync.
3. Sau target I/O, helper gửi `ready_to_finalize` khi còn lock. Daemon lưu terminal ledger bền vững rồi gửi `FINALIZE`. Exact retry cùng payload đọc record hoặc attach vào lượt đang chạy. Cùng ID khác payload trả `operation_mismatch` trong cùng binding. Journal lưu hash của binding và preview ID, cùng fingerprint/mode/lineage và evidence về inode khi có. Source bytes và opaque preview token không được ghi vào journal.
4. Sau restart, record còn ở `accepted`, `preflight` hoặc `writing` được chiếu thành `recovery_required` khi đọc, giữ ledger durable và `targetMutated: "unknown"`. Terminal record được trả nguyên. Record thiếu, ngoài scope hoặc đọc không được trả `outcome_unknown`. Không tự resume, xóa file đích hay suy ra zero writes từ RPC disconnect.

[Journal](server/apply-journal.ts) giữ tối đa 64 records, mỗi record tối đa 2 MiB, rồi từ chối admission mới. Fixture giữ records cho tới khi dọn home. Chính sách prune terminal sau 24 giờ của proposal chưa chạy trong fixture. Durability dùng file/directory `fsync` và được nghiệm thu qua process kill và restart. Chưa thử power loss hoặc fsync failure thật. Fault journal trước ACK thu hồi quyền của private journal directory để kiểm fail-closed.

Worker `--worker` bắt buộc dùng durable admission. `--primitive-fixture-worker` chỉ phục vụ harness primitive M4.3 và vẫn chịu fixture gate. Platform/version/integrity gate M4.3 giữ nguyên. Không có Node full-path target writer. Native helper vẫn có giới hạn của directory pinning khi rename xảy ra sau lần linkage check cuối. Khóa này serialize các plugin trong cùng fixture daemon home, trong trust boundary cooperative filesystem và UID của plugin.

## Nghiệm thu

**Paseo 0.17.5, SDK client/plugin/protocol 0.17.4, Node 24.20.0 / Electron 44.2.0 trong plugin subprocess, macOS 27.2.1 (26B131), arm64, local APFS case-insensitive.** Driver chạy daemon thật trên loopback, dùng settings và catalog fixture có thể đổi để kiểm stale. Catalog loader mạng và Apply UI nằm ngoài lượt nghiệm thu.

| Nhóm | Evidence đã xác minh |
| --- | --- |
| Hai callers, hai subprocess | Exact duplicate cùng kết quả, payload mismatch bị từ chối, slot khác không đọc được status, cùng receipt chỉ một claim. Peer nhận busy trước claim rồi dùng lại cùng receipt thành công. |
| Receipt và Kiro | Settings revision, pinned SHA, read-set và Git root proof đổi đều cho terminal stale trước write. Conflict/blocked giữ nguyên tree. Kiro hợp lệ tạo đúng canonical/derived bytes, mode và lineage, Git tree giữ nguyên. |
| Late collision | Foreign binary leaf xuất hiện tại barrier trước exclusive create. Writer từ chối, tree giữ nguyên hash/mode/dev/ino. |
| Journal lỗi trước ACK | Private directory validation từ chối publish. Target tree giữ nguyên, Status không có record. Sau phục hồi quyền, receipt đó dùng được với operation ID khác. |
| Partial write | `ENOSPC` sau 1 byte. Ledger ghi file hiện tại dở và các file sau chưa thử. Existing entry giữ nguyên. |
| Mất reply sau terminal | Client đóng kết nối sau khi client thứ hai đã đọc được terminal record và trước khi handler trả reply. Exact retry trả cùng terminal record cả trước và sau restart. |
| Crash sau create | Kill plugin parent tại native barrier sau exclusive create và trước verified progress ACK. Leaf rỗng mode `0600` giữ nguyên qua restart. Status và exact retry trả `recovery_required`. Operation mới sau restart lấy lại cùng lock inode. |
