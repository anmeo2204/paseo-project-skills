## 2. Format và discovery

1. Tại commit đã resolve, liệt kê Git tree với output NUL-delimited và kích thước blob. Xác thực `skills` là tree và duyệt các thư mục con trực tiếp. Mỗi thư mục skill cần file `SKILL.md` chính xác ở cấp đầu. Cây `skills/` thiếu, rỗng, hoặc có thư mục ứng viên thiếu entrypoint được báo là catalog lỗi. Root docs và file thường ở ngay dưới `skills/` không phải skill. [Git ls-tree](https://git-scm.com/docs/git-ls-tree)
2. Dùng slug thư mục làm ID trong phạm vi nguồn cố định. Slug dài tối đa 64 ký tự, theo mẫu `^[a-z0-9]+(?:-[a-z0-9]+)*$`. ID giữ nguyên qua các commit khi thư mục giữ nguyên tên. Rename tạo ID mới. Kiểm tra uniqueness của path, ID và tên khai báo. Ví dụ, hai thư mục khai báo cùng `name` được báo trùng và tên lệch thư mục được báo sai metadata.
3. Đọc `SKILL.md` dưới dạng UTF-8 nghiêm ngặt. Tách frontmatter mở bằng `---` ở đầu file và yêu cầu delimiter đóng. Đề xuất khai báo trực tiếp parser `yaml` trong package khi triển khai, kiểm tra lỗi parse, yêu cầu một mapping, từ chối duplicate keys, aliases, custom tags và merge keys. Dùng Zod kiểm tra `name` theo slug, bằng tên thư mục, và `description` là chuỗi có nội dung, tối đa 1.024 ký tự. Giữ nguyên Markdown gốc. Các trường bổ sung có thể tồn tại trong YAML hợp lệ và chưa được diễn giải ở M2.1.
4. Supporting files là mọi blob thường bên dưới cùng thư mục skill, trừ entrypoint. Đường dẫn giữ tương đối với thư mục skill, kể cả thư mục lồng. Loader đọc theo blob OID đã kiểm tra trong tree. Liên kết Markdown và URL trong nội dung được giữ dưới dạng text. Quy tắc này tự nhận skill mới ở bất cứ nhóm nào nếu đúng convention.
5. Sắp xếp skill theo ID, file theo path với thứ tự cố định. Nếu có lỗi cấu trúc, metadata hoặc ID, trả lỗi kèm chẩn đoán giới hạn số mục và path an toàn. Chỉ trả và cache snapshot khi toàn bộ catalog hợp lệ.

## 3. Resolve revision và truy xuất

Dùng Node `child_process` và Git sẵn trên daemon. Giữ `catalogSource` làm định danh nguồn cố định. Đề xuất ánh xạ URL hiện tại sang SSH cố định `git@github.com:anmeo2204/project-skills.git`, cùng repo với origin đã xác minh. Dùng SSH không tương tác với quyền đọc và kho known_hosts đã cấu hình trên host. Plugin không cung cấp trường nhập credential. Lần khảo sát đọc remote thành công từ terminal qua SSH. HTTPS của terminal thất bại vì thiếu credential, và trình duyệt công khai trả 404. Tiến trình daemon cần được xác minh riêng vì môi trường SSH có thể khác terminal.

- **Chung.** Handler đọc host settings đúng một lần khi nhận request. Dùng lại schema M1, đặt giới hạn chiều dài ref ở loader và chuẩn hóa SHA về chữ thường. Giá trị trống báo `not_configured`. Bare name chỉ có nghĩa là tag. Ví dụ `main` hợp lệ nếu có tag cùng tên. Explicit branch ref, biểu thức Git và SHA viết tắt bị từ chối theo schema M1.
- **Full SHA.** Dùng cache đã xác thực của đúng SHA nếu có. Khi miss, chỉ fetch OID 40 hex từ nguồn cố định. Xác minh object tải về đúng SHA và có type trực tiếp là `commit`. Một SHA của annotated tag object cũng bị từ chối ở nhánh này.
- **Tag.** Fetch đúng `refs/tags/<name>` vào một ref riêng trong bare repo tạm, với `--no-tags` để tắt auto-follow. Dùng ref nội bộ vừa fetch để peel theo `^{commit}` và yêu cầu kết quả là commit SHA đầy đủ. Lightweight tag trỏ thẳng đến commit, còn annotated tag được peel đến commit. Tag trỏ blob/tree bị từ chối. Mỗi lần gọi theo tag resolve lại qua remote. Tag đổi trong lúc đọc vẫn dùng đúng SHA đã chốt trong lần fetch đó.
- **Git staging.** Dùng bare repo SHA-1 tạm riêng cho cache miss hoặc tag resolution, dưới temp của daemon, với shallow fetch `--depth=1`, explicit refspec, không checkout và không recurse submodule. Liệt kê tree và đọc blob chỉ sau khi xác thực commit. Dọn staging khi hoàn tất hoặc lỗi. Dùng staging riêng theo lượt resolve để tránh race giữa các tag/ref. Nếu upstream từ chối fetch SHA được yêu cầu, trả lỗi cho chính SHA đó. [Git fetch](https://git-scm.com/docs/git-fetch)
- **Lỗi.** Missing tag, SHA không truy xuất được hoặc object sai type trả `revision_unavailable` khi xác định được nguyên nhân. Auth, transport và timeout có mã riêng; lỗi Git khó phân loại trả `git_error`. Mọi retry lặp lại đúng thao tác theo input được chọn. Với tag đã resolve trong request hiện tại, phần đọc/retry chỉ dùng SHA đã chốt. Không fallback sang branch, HEAD, main, latest hoặc revision cache khác.

## 4. Snapshot đề xuất

| Kiểu | Trường |
| --- | --- |
| `CatalogSnapshot` | `schemaVersion: 1`, `source` là URL cố định, `commitSha` là 40 hex chữ thường, `skills: CatalogSkill[]` |
| `CatalogSkill` | `id`, `directory` là repo-relative path, `metadata: { name, description }`, `entrypoint: CatalogFile`, `supportingFiles: CatalogFile[]` |
| `CatalogFile` | `path` tương đối với thư mục skill, `blobSha`, `sizeBytes`, `mode` là Git regular-file mode, `bytes` là Buffer nội bộ daemon |

Snapshot server chứa đủ dữ liệu của cùng commit cho phase sau. Bản RPC chỉ chiếu metadata và file descriptors, bỏ `bytes` của mọi file. Giá trị `requestedRef` và `settingsRevision` chỉ thuộc envelope của request, nên cùng SHA cho cùng snapshot dù input là tag hay SHA. Schema chưa chứa nhóm suy diễn từ slug, timestamp, dữ liệu provider, dependency hoặc compatibility.

## 5. Cache và security

- **Cache tối thiểu trong bộ nhớ subprocess.** Key là source cố định + resolved SHA; schema chỉ sống trong vòng đời phiên bản loader. Giữ tối đa 2 snapshot (LRU), mỗi snapshot tối đa 8 MiB bytes. Khi đã có SHA, gộp lượt parse đồng thời theo cùng key nếu cần. Chỉ publish sau khi toàn bộ dữ liệu qua validation. Promise thất bại được loại bỏ, không cache lỗi hoặc snapshot dở dang. Cleanup hủy tiến trình con đang chạy và thu hồi cache. Temp bị bỏ lại sau kill cứng không được reuse. Với SHA trực tiếp, cache hit có thể phục vụ khi mất mạng; với tag, lỗi resolve trả lỗi dù cache còn SHA từng được tag trỏ tới. Restart plugin làm cache rỗng.
- **Ranh giới đọc.** Duyệt tree qua Git và đọc raw blob bằng OID kiểm chứng, dùng cú pháp không dereference path qua filesystem. Reject symlink, gitlink/submodule và mode lạ trong phần cây được tải. Validate UTF-8 path theo từng segment, reject segment rỗng, `.`, `..`, dạng tuyệt đối/drive, backslash, control chars và tên dành riêng cho metadata Git. Kiểm tra path nằm dưới đúng thư mục skill. Không giải nén archive, checkout, chạy filter, đọc link tham chiếu, hoặc chạy code từ catalog. [Git cat-file](https://git-scm.com/docs/git-cat-file)
- **Cô lập Git.** Spawn argv với shell tắt, cwd và Git dir chỉ tới staging do plugin tạo, quyền riêng của host user. Chặn Git env/config có thể đổi repo, object store, URL hoặc protocol; whitelist SSH cho production, tắt replacement refs, hooks và template bên ngoài. Chỉ cho kế thừa những tham số môi trường cần thiết cho SSH host auth, dùng batch mode và host-key verification. Dùng URL cố định, ref đã validate, Git output có giới hạn và lỗi đã lược bỏ stderr raw. Test có seam cho transport fixture local, production không nhận URL/path tùy ý.
- **Giới hạn ban đầu.** Tối đa 512 skill, 2.048 entries dưới `skills/`, 1 MiB mỗi blob, 128 KiB mỗi `SKILL.md`, 8 MiB tổng blob được đọc, path 512 byte, ref 256 byte. Giới hạn danh sách trước khi đọc blobs, xác thực size và số byte thực nhận. Giới hạn tổng RPC descriptor JSON ở 512 KiB và xác minh với daemon thực. Giới hạn thời gian toàn lượt tải lạnh 20 giây, tối đa hai lượt staging đồng thời, với tổng dung lượng staging được kiểm tra trong fetch và hủy nếu vượt ngưỡng khởi điểm 64 MiB mỗi lượt. Kiểm tra dung lượng định kỳ là ngưỡng vận hành, có thể vượt ngắn hạn giữa hai lần đo. Các ngưỡng dựa trên tree khảo sát và sẽ được xác minh bằng fixture. Trả `limit_exceeded` khi vượt ngưỡng; staging lỗi được dọn, retry tạo staging mới.
- **Tác động filesystem.** Chỉ ghi staging ngoài checkout và ngoài target project. Loader không nhận target cwd, không lần theo working tree Project-Skills và không ghi dữ liệu catalog vào settings.

## 6. RPC contract và tích hợp M1

Dùng `defineRpc` và Zod với `catalog.load`. Input là `z.strictObject({})`. `index.server.ts` giữ handle do `server.registerSettings(catalogSettings)` trả về rồi gọi `read()` trong handler. SDK 0.17.4 công bố `read(): Promise<PluginSettingsState<Schema>>`, gồm `status`, revision của settings document và values hoặc lỗi. Ref lấy từ settings host đã lưu, không lấy draft hay input gọi RPC.

- **Ready** — `{ status: "ready", settingsRevision, requestedRef, snapshot }`. Snapshot dạng descriptor như mục 4. Client tương lai có thể đối chiếu `settingsRevision` khi kết quả đến sau lần đổi settings.
- **Error** — `{ status: "error", code, settingsRevision?, requestedRef?, diagnostics? }`. Mã gồm `not_configured`, `invalid_settings`, `invalid_revision`, `revision_unavailable`, `git_unavailable`, `auth_failed`, `network_error`, `timeout`, `git_error`, `invalid_catalog`, `limit_exceeded`, `host_io_error`. Diagnostics có mã cụ thể như `duplicate_skill_id`, `malformed_metadata`, `unsafe_entry` và path tương đối khi an toàn. Trạng thái transport offline của Paseo vẫn qua cơ chế transport hiện có.

RPC và service chạy trong subprocess plugin trên daemon host, tái sử dụng settings M1. Client M1 giữ luồng Save hiện tại. Loader độc lập với scanner, agent session, provider, recommendation, SLP và Kanbanly. [Paseo Plugin Reference 0.17.4](https://github.com/getpaseo/paseo/blob/v0.17.4/public-docs/plugins/reference.md)

## 8. Test và nghiệm thu

- **Resolve bằng Git fixture tạm.** Hai commit, lightweight tag, annotated tag, tag lồng namespace, tag cùng tên branch và một bare name chỉ tồn tại ở branch. Xác nhận đúng SHA, reject SHA không có, SHA rút gọn, tag thiếu, branch-only, full SHA của object không phải commit, và tag trỏ non-commit. Kiểm tra tag bị di chuyển hoặc xóa giữa các lượt.
- **Discovery và dữ liệu.** Thêm skill tên mới và supporting file lồng không cần thay loader. So sánh bytes, kích thước và mode của entrypoint và hỗ trợ, gồm file nhị phân. Ca lỗi gồm thiếu entrypoint, slug sai, slug/name lệch, khai trùng tên, frontmatter hỏng, duplicate YAML keys, alias, UTF-8 lỗi và metadata sai type/length. Kiểm tra file ngoài cây skill và ứng viên chỉ ghi trong README không được trả về.
- **Boundary và cache.** Fixture symlink trỏ ra ngoài, gitlink, path độc hại, output lỗi/truncated, vượt giới hạn count/size/time và Git thiếu. Xác nhận cache hit cùng SHA trả snapshot bằng nhau, A/B không trộn, cache chỉ publish khi thành công, lỗi/timeout dọn staging, retry đúng SHA, tag offline/mất tag không dùng ánh xạ cũ, tải đồng thời và eviction đúng giới hạn. So sánh HEAD, status và nội dung sentinel của checkout catalog và target trước/sau. Xác minh không chạy code/filter từ fixture.
- **RPC và regression.** Kiểm tra strict input, output Zod, settings trống/hỏng, routing theo host settings và failure mapping. Chạy `npm run typecheck` và toàn bộ `npm test`, giữ 15 kịch bản Foundation hiện có.
- **Nghiệm thu local daemon 0.17.4.** Kiểm tra plugin load với parser YAML; gọi typed RPC bằng đường gọi thử nghiệm trên đúng daemon với SHA `7f36043f2c18d4bf4c245a5a474c898244c83590`. Đối chiếu 19 IDs, 21 supporting files và descriptor với tree đã khảo sát. Thử lại cùng SHA, rồi revision sai. Kiểm tra Foundation vẫn chạy và khôi phục settings trước smoke test. Lightweight/annotated tag được nghiệm thu bằng fixture vì remote hiện chưa có tag. Smoke test không cần tạo tag upstream.

## 9. Blocker và quyết định chờ phê duyệt

1. **Transport** — Phê duyệt SSH cố định cho cùng catalog source và dùng host auth sẵn có. Quyền fetch SHA từ tiến trình daemon, bao gồm khả năng thấy SSH agent hoặc identity và known_hosts, chưa được xác minh. Nếu daemon không có quyền, live acceptance bị chặn ở bước truy cập repo. Automated fixtures vẫn kiểm tra được loader và không cần credentials.
2. **Parser và policy lỗi** — Phê duyệt một dependency YAML trực tiếp, với smoke test đóng gói Paseo 0.17.4, và policy trả lỗi toàn snapshot khi phát hiện skill malformed/trùng ID. M2.1 chỉ diễn giải `name` và `description` có thật ở catalog hiện tại.
3. **Cache và scope RPC** — Phê duyệt cache memory hai commit theo SHA, resolve tag lại trên mỗi lượt và chỉ gửi descriptor qua RPC. Snapshot nội bộ giữ bytes cùng commit để phase sau có thể dùng trực tiếp.

Dừng ở kế hoạch và chờ phê duyệt M2.1.
