## 3. Shared Component and State Ownership Design

### Single Authoritative Tree (Zero State Duplication, Zero Remount on Resize)

A key safety requirement is: **layout changes (`layout.compact: false ↔ true`) and Mobile step navigation (`Setup ↔ Skills ↔ Preview`) must NEVER unmount stateful subtrees or invalidate a valid Preview!**

- **Architecture:**
  1. `HostScreen` keeps **one** React tree structure across both Desktop and Mobile:
     - Outer wrapper `<View style={{ flexDirection: compact ? "column" : "row", alignItems: compact ? "stretch" : "flex-start", gap: 16 }}>`.
     - **Pane A (`configPane`):** `Target Project`, `Target Providers`, `Skill Catalog`, `ConnectionCheck`.
       - On Desktop: `width: 340, flexShrink: 0, display: "flex"`.
       - On Mobile: `width: "100%", display: mobileStep === "setup" ? "flex" : "none"`, `aria-hidden={mobileStep !== "setup"}`, `importantForAccessibility={mobileStep !== "setup" ? "no-hide-descendants" : "auto"}`.
     - **Pane B (`workPane`):** Compact Context Bar + `<RecommendationRun ... mobileStep={compact ? mobileStep : undefined} />` + `<FixtureOperations />`.
       - On Desktop: `flex: 1, minWidth: 0, display: "flex"`.
       - On Mobile: `width: "100%", display: mobileStep !== "setup" ? "flex" : "none"`.
  2. Inside `RecommendationRun` (staying mounted in the exact same tree slot!):
     - **Skills sub-pane** (`Scan & Recommend` + `RecommendationResults`): visible on Desktop OR when `mobileStep === "skills"` (hidden with `display: "none"` when `mobileStep === "preview"`).
     - **Preview sub-pane** (`PreviewRun` / `FixtureApprovalPreview`): visible on Desktop OR when `mobileStep === "preview"` (hidden with `display: "none"` when `mobileStep === "skills"`).
  3. **Why this works cleanly:**
     - Switching `layout.compact` from `false` to `true` (e.g., resizing Desktop window) only changes `style` props — React **never** unmounts `CatalogSection`, `ProviderSelection`, `RecommendationRun`, `RecommendationResults`, `PreviewRun`, or `FixtureApprovalPreview`!
     - Navigating `Setup ↔ Skills ↔ Preview` on Mobile preserves `selected`, search/filter state, and any valid `Preview` receipt without re-fetching or re-scanning!
     - `FixtureOperations` remains mounted so live operation tracking (`useSyncExternalStore`) never drops updates; on Mobile, an active/recovery operation notice in the step header links straight to Step 3 (`Preview & Apply`).

## 4. Navigation and Invalidation Behavior

| Action | Navigation Effect | State / Invalidation Effect |
| --- | --- | --- |
| **Desktop window resize (`compact` toggles)** | Switches between two-pane and 3-step view. | **Zero invalidation.** Active target, providers, scan, selection, Preview, and Approval receipt remain intact. |
| **Mobile: `Setup → Skills` (`Continue to Skills`)** | Sets `mobileStep = "skills"`. | **Zero side effects.** Does NOT auto-scan, auto-preview, or auto-apply. |
| **Mobile: `Skills → Preview & Apply`** | Sets `mobileStep = "preview"`. | **Zero side effects.** Does NOT auto-preview, auto-approve, or auto-apply. User must explicitly click **Preview Changes**. |
| **Mobile: `Preview & Apply → Skills` → `Preview & Apply`** | Moves back and forth without changing selection. | Preserves `selected` AND preserves any valid unexpired Preview receipt. |
| **Any actual intent mutation** (change target, change providers, pin new catalog, toggle/select/clear skills) | Stays on current step (no surprise jumps). | Existing `scope`, `selectionGeneration`, `providerGeneration`, and `settings.revision` guards **immediately invalidate** stale Scan/Preview/Approval state exactly as in M4/M5.1–M5.3. |
| **Host switch or disconnect** | `HostScreen` unmounts (`key={host.id}`); `mobileStep` resets to `"setup"`. | All host-scoped state, active requests, and receipts discard cleanly. |

## 5. Preview and Approval Presentation

1. **Concise Status Summary Strip (`client/preview-results.tsx`):**
   - Replace the single muted text summary with distinct, scannable status badges/chips (`flexDirection: "row", flexWrap: "wrap", gap: 6`):
     - `Create: N`
     - `Unchanged: N`
     - `Conflict: N` *(styled with `statusDanger` border/text whenever `N > 0`)*
     - `Blocked: N` *(styled with `statusDanger` border/text whenever `N > 0`)*
   - When `Conflict > 0` or `Blocked > 0`, display an explicit top-level danger banner: *"Blocking conflicts or blocked destinations detected. Safe Apply cannot proceed until resolved."* — **never collapsed or hidden**.
2. **Reduced Boilerplate, Full Safety Details Accessible:**
   - Keep exact `Target` (canonical directory), full selectable `Pinned catalog` SHA, `Skills selected`, `Target providers`, `Planned directories`, `Canonical files`, `Kiro derived files`, `Provider compatibility`, and `Preview diagnostics` accessible.
   - In `ReviewPlan` (`client/fixture-approval.tsx`), pass `hideHeaderScope` to `PreviewResults` so Target and Pinned SHA aren't printed twice back-to-back while remaining 100% visible in `Planned Changes` and `Create-only Approval`.
   - Preserve `PagedEffects` pagination (25 items/page) and per-file `Disclosure` (`Preview details for <destination>`) with full byte size, POSIX mode, SHA-256, and horizontal-scroll monospace unified diff.
3. **Approval & Operation Tracking (`client/fixture-approval.tsx`):**
   - Keep the two-step explicit approval flow (`Review create-only approval` → `Confirm create-only`), receipt expiration warning, and `Apply Operations` ledger/recovery controls completely intact.

## 6. Accessibility and Responsiveness Requirements

- **Touch Targets:** All step tabs, navigation buttons (`Continue to Skills`, `Back to Setup`, `Preview & Apply`, `Back to Skills`), filter pills, and checkboxes maintain `minHeight: 36`–`40` with wrapped rows (`flexWrap: "wrap"`).
- **Screen Readers & Focus:**
  - Step bar uses `accessibilityRole="tablist"` / `accessibilityRole="tab"` with `accessibilityState={{ selected }}` and clear labels (`"Step 1: Setup"`, `"Step 2: Skills"`, `"Step 3: Preview & Apply"`).
  - Hidden Mobile steps set `aria-hidden={true}` and `importantForAccessibility="no-hide-descendants"` alongside `display: "none"`.
  - Live status updates (`Preparing read-only preview…`, `Selected skills: N`, operation phase titles) retain `accessibilityLiveRegion="polite"`.
- **Keyboard & Scrolling:**
  - Single outer `<ScrollView>` with `keyboardShouldPersistTaps="handled"` so tapping buttons while a search/path keyboard is open works in one tap on Mobile.
  - Diff viewer keeps bounded `maxHeight: 300` and horizontal `<ScrollView>` so long diff lines never cause page-wide horizontal overflow on `390×844` screens.

## 8. Failure Scenarios and Safety Analysis

| Scenario | Expected Behavior |
| --- | --- |
| **User resizes Desktop window across compact threshold with active Preview/Approval** | Single mounted tree toggles styles only; valid Preview receipt and Approval state are preserved without invalidation or re-fetch. |
| **Mobile user navigates `Preview → Skills → Preview` without changing selection** | Selection and valid Preview receipt remain intact; navigating back to `Preview` does NOT re-run `preview.providers.v2` automatically. |
| **Mobile user navigates `Preview → Setup` and changes Target, Providers, or Catalog** | Existing `HostScreen` / `RecommendationRun` / `PreviewRun` guards immediately invalidate Scan/Preview/Approval even while Step 3 is hidden; returning to Step 3 shows fresh un-previewed state. |
| **Plan has `Conflict` or `Blocked` files** | Top-level danger banner and `Conflict`/`Blocked` badges are always visible above the file list; `Create-only Approval` remains disabled/ineligible. |
| **Active or `recovery_required` Apply operation while Mobile user is on Step 1 or Step 2** | Step header shows a visible non-dismissible banner linking straight to `3. Preview & Apply` so operation status and recovery ledger are never hidden. |
| **Host disconnects or switches while on Step 2 or Step 3** | `HostScreen` unmounts cleanly, `mobileStep` resets to `"setup"`, and `FixtureOperations` remains visible outside `HostScreen` as before. |

## 10. Decisions Requiring User Approval

1. **Desktop Two-Pane Breakpoint & Widths:**
   - **Recommended:** Use Paseo SDK's `layout.compact` flag (`!layout.compact` → two-pane with `340px` left config pane + `flex: 1` right working area inside `maxWidth: 1240`; `layout.compact` → 3-step Mobile workflow).
   - **Alternative:** Add a separate client-measured width breakpoint (e.g., `useWindowDimensions()`) in addition to `layout.compact`.
2. **Mobile Step Gating (Free Navigation vs Strict Gating):**
   - **Recommended:** Allow tapping any step pill freely (so users can always jump to Step 3 to inspect `Apply Operations` or check status), while showing clear inline guidance when a prerequisite (like Target Directory or Selected Skills) is not yet complete.
   - **Alternative:** Strictly disable Step 2 until a Target Directory is validated and disable Step 3 until ≥1 skill is selected (except when an Apply operation is active).
3. **Keeping Inactive Mobile Steps Mounted (`display: "none"`):**
   - **Recommended:** Keep all 3 Mobile step subtrees mounted with `display: "none"` + `aria-hidden` so layout resizes and backward/forward navigation never lose valid Preview receipts or filter state without introducing a global state store or navigation framework.
   - **Alternative:** Lift `PreviewRun` / `FixtureApprovalPreview` state into `HostScreen` and conditionally unmount inactive steps.

Please review and confirm these decisions before I begin M5.4 implementation.
