## 3. Rule parser

Parser lấy exact supporting blob `applicability.json` cạnh `SKILL.md` trong pinned snapshot. Giới hạn từng file là 8.192 bytes. UTF-8 được decode ở chế độ fatal. JSON grammar loại BOM và cú pháp sai. Một lượt duyệt token kiểm tra duplicate keys theo tên đã decode escape trong mỗi object, kể cả object lồng. Schema strict kiểm tra version, shape, field names, selector literals và giới hạn 4×4 cho mỗi condition.

Metadata thiếu trả `missing_applicability`, file sai trả `invalid_applicability`, version nguyên ngoài v1 trả `unsupported_rule_version`. Mỗi diagnostic tạo verdict `unknown` cho skill tương ứng. Rule được đọc như dữ liệu và xử lý tách biệt theo skill.

## 4. Evaluator

Evaluator chạy đồng bộ từ snapshot và ProjectEvidence. Sau khi validate, engine index refs theo ID, facts theo boundary và kind, và inventory theo Skill ID. Rule server dẫn xuất từ snapshot được đánh giá trên dữ liệu này. Output dùng thứ tự bytewise và liệt kê đúng một item mỗi skill trong snapshot. Engine dùng vocabulary chung của scanner, nên catalog có thể thêm skill mới bằng metadata.

## 5. Recommendation semantics

Project scope dùng `level` tại root `.` với reason `reusable_workflow`. Boundary scope dùng OR của các nhóm AND. Selector so khớp literal với kind, basis, key và các filter khai báo. `sourceFile` so basename của ref thuộc fact đang khớp. Engine chỉ xét `recommendWhen` sau khi `appliesWhen` khớp cùng boundary.

Mỗi skill giữ mọi positive boundary match. Verdict tổng ưu tiên `recommended`, rồi `optional`, rồi `unknown`. Positive evidence tiếp tục có giá trị khi coverage partial. Thiếu evidence đưa ra reason `partial_evidence` hoặc `no_supported_evidence`. V1 phát ba verdict và luôn đặt `taskApplicability: "not_assessed"`.

## 6. Evidence integrity

Engine kiểm tra schema, ID trùng, relative paths, root boundary, fact/inventory ownership, workspace membership và reference integrity. Fact chỉ tham gia evaluation tại boundary scanner đã gán. Cross-boundary ref cần workspace membership hợp lệ, chẳng hạn Angular member có provenance từ manifest root. Engine kiểm tra Skill ID, exact entrypoint/sidecar descriptors, byte length và Git blob SHA. Catalog commit và settings revision được ghi trong envelope. Positive reasons trace tới blob catalog và evidence index chứa các ref đã dùng.

Giới hạn là 512 skills, 64 boundaries, 256 KiB ProjectEvidence và 512 KiB recommendation event. Nếu scanner báo đã vượt budget khi chiếu evidence, hoặc recommendation vượt budget, subscription trả `limit_exceeded`.

## 7. Inventory

Inventory giữ riêng trạng thái `present`, `multiple_occurrences`, `not_observed` hoặc `unknown`. Mỗi occurrence giữ layout, path, boundary, refs, match type và flags. ID thư mục và declared ID phải khớp cùng metadata hợp lệ để xác nhận. Mismatch, malformed và unreadable tạo candidate khi nhận diện được ID. `possible_customization` đến từ review signal của scanner. Partial coverage giữ positive occurrences và khiến absence chưa đủ căn cứ. Verdict applicability độc lập với installation state.

## 8. RPC và lifecycle

`recommendation.evaluate` dùng strict input với request ID, canonical directory và hai precondition tùy chọn. Mỗi request đọc host settings, resolve catalog một lần, tái scan trên daemon và kiểm tra lại settings revision trước publish. Daemon dùng chung loader và scanner với hai route hiện có. Kết quả recommendation được tính lại cho từng request.

Mỗi installation có một slot. Abort chuyển vào scanner và chặn publish khi request hết hiệu lực. Nếu loader đang chạy, slot giữ đến khi công việc settle. Request có hiệu lực nhận một terminal event. Client SDK runtime kiểm tra release/disconnect và A → B → A bằng request IDs riêng. Scope M2.4C chỉ có daemon route và SDK contract.
