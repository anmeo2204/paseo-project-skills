### 1.2 Focused Source & Regression Audit Findings (P6, P7, P8)

Per instruction, **zero code changes were made during this audit**; all confirmed defects are reported below for explicit approval before remediation.

#### P6 — Mutable Journal Pagination: **PASS (No Code Defect Found)**
- **Client deduplication:** `createOperationTracker.ingestDiscovered()` (`client/apply-tracker.ts:156-169`) looks up each incoming summary by `operationId` (`next.findIndex((row) => row.operationId === summary.operationId)`), updating in place rather than appending duplicates across overlapping pages or refreshes.
- **Mutable priority / phase / `updatedAt` between pages:**
  - `listJournalSummaries()` (`server/fixture-apply.ts:45-60, 103-128`) ranks `accepted`/`preflight`/`writing`/`partial_failure`/`recovery_required` in priority bucket `0` ahead of `completed`/`failed_before_write` in bucket `1`, ordered by `(priority ASC, updatedAt DESC, operationId ASC)` with keyset cursor `priority:updatedAt:operationId`.
  - If an active operation transitions from bucket `0` to bucket `1` (`completed`) between page 1 and page 2, it may reappear on page 2 and is safely deduplicated and merged by `operationId`.
  - If a new active or recovery-required operation appears in bucket `0` while the user is browsing bucket `1` (`completed` history), clicking `Refresh operations` (or reconnecting / switching back to the host) calls `discover()` with `cursor = undefined`, which fetches from the top of bucket `0` first. Because `ApplyJournal` caps total records at `64` and Apply is single-flight, bucket `0` items fit on page 1 (`limit = 20`) and locally tracked active operations are also polled directly via `apply.status.v1`.
- **Conclusion:** Existing refresh + priority-0-first keyset pagination + client `operationId` deduplication satisfies P6 without introducing server-side snapshot state.

#### P7 — Concurrent Response Freshness: **2 CONFIRMED DEFECTS (Require Targeted Fix Before v0.3.0)**
1. **Defect P7-A — Same-phase `summary` → `summary` staleness (`client/apply-tracker.ts:180`):**
   - `ingestDiscovered()` checks only `if (existing.summary && incomingRank < existingRank) continue;`.
   - When two `writing`-phase summaries arrive with equal `phaseRanks` (`2`), `incomingRank < existingRank` is `false`, allowing a delayed summary with an older `updatedAt` (e.g. `updatedAt: 1000`) to overwrite a fresher summary (`updatedAt: 2000`).
2. **Defect P7-B — Same-phase `operation` → `operation` staleness & unguarded `lookup()` concurrency (`client/apply-tracker.ts:96-98, 206-242`):**
   - Both `settle()` (line 97) and `lookup()` (line 228) rely exclusively on `phaseRanks` (`accepted: 0`, `preflight: 1`, `writing: 2`, all 4 terminal phases: `3`). During `writing`, a delayed `apply.status.v1` or `apply.create.v1` response with fewer progressed ledger entries (more `not_attempted` rows) has the same rank (`2`) and overwrites a fresher `writing` response with more progressed ledger entries.
   - `lookup()` does not participate in `statusRequests` request-token tracking and lacks `settle()`'s `if (terminal(current) && !(allowLedgerHydrate && !current.operation)) return;` guard (line 90), allowing an out-of-order `lookup()` response to race with `check()` / `submit()` or overwrite an already-settled full `ApplyOperation`.
- **Proposed Minimal Fix (Pending User Approval):**
  - Add a pure freshness comparator in `client/apply-tracker.ts`:
    - For `summary` vs `summary` at equal `phaseRanks`: require `incoming.updatedAt >= existing.updatedAt` (and never regress `targetMutated: true` → `false`).
    - For `operation` vs `operation` at equal `phaseRanks`: never overwrite an existing terminal full `ApplyOperation`; for non-terminal same-phase (`writing`), compare monotonic ledger progress (count of entries with `state !== "not_attempted"` and total `bytesWritten`), rejecting strictly older responses.
    - Bind `lookup()` to `statusRequests` with a per-request token (or monotonic per-operation request sequence) and guard `if (terminal(existing) && existing.operation) return;` before `put()`.
  - Add targeted P7 regression tests in `tests/operation-tracking.test.mjs` covering: same-phase `writing` delayed responses (both `list → status` and `status → list`), concurrent `lookup()` + `check()` + refresh races, and daemon restart recovery (`writing` → `recovery_required`).

#### P8 — Journal Resource & Filesystem Safety: **1 CONFIRMED DEFECT + 1 EVENT-LOOP RISK (Require Decision Before v0.3.0)**
1. **Defect P8-A — Unbounded directory enumeration before `maxDirectoryEntries` (`server/apply-journal.ts:81-85`):**
   - `ApplyJournal.list()` calls `readdirSync(this.directory).sort()` before checking `allNames.length > limits.maxDirectoryEntries`. If the coordinator directory accumulates thousands of stray/temp entries, Node allocates and sorts the entire directory array before slicing to `256`.
   - **Proposed Minimal Fix (Pending User Approval):** Replace `readdirSync(this.directory)` with `opendirSync(this.directory)` + bounded `dir.readSync()` loop stopping at `limits.maxDirectoryEntries + 1` (setting `truncated = true` when an extra entry exists, closing `dir` in `finally`), then sorting only the bounded array.
2. **Risk P8-B — Synchronous filesystem I/O event-loop impact (`server/apply-journal.ts:70-158`):**
   - `ApplyJournal.list()` performs synchronous `openSync` / `fstatSync` / `readSync` / `closeSync` for up to `64` records / `16 MiB` / `2000 ms` inside a single event-loop turn.
   - Under normal local APFS workloads (≤ 64 small JSON files, < 320 KiB total), this completes in ~1–5 ms. Under worst-case `16 MiB` reads or contended I/O, it can block the daemon event loop for up to `2 s`.
   - **Proposed Options (Pending User Approval):**
     - **Option A (Recommended):** Convert `ApplyJournal.list()` (or add `listAsync()`) to yield cooperatively between records (e.g. async `fs/promises` `opendir`/`open(O_RDONLY | O_NOFOLLOW | O_NONBLOCK)`/`fstat`/`read` or `setImmediate` yield every 8 records) while preserving all `O_NOFOLLOW`, `fstat`, ownership/mode, pre/post `checkDirectory()`, and read-only guarantees.
     - **Option B:** Keep synchronous reads for simplicity after fixing P8-A (`opendirSync`), and tighten `maxDurationMs` from `2000 ms` to `500 ms` to cap worst-case single-turn blocking.
3. **Verified Safe under P8:**
   - File identity during concurrent journal replacement: `readEntryReadOnly()` (`server/apply-journal.ts:129-157`) opens with `O_RDONLY | O_NOFOLLOW | O_NONBLOCK`, validates `fstatSync(fd)` on the descriptor (regular file, `nlink <= 2`, owner UID, `0o600`, `size <= maxBytes`, `size <= remainingBytes`) **before** `Buffer.alloc`, reads from `fd`, verifies `record.operation.operationId === parsedId.data`, and relies on atomic `renameSync` writes + pre/post `checkDirectory()` identity checks.
   - Strictly read-only discovery: zero `unlink`, `rename`, `write`, or `fsync` calls in `list()` / `readEntryReadOnly()`.

## 4. Physical Mobile Device Test Procedure (Step-by-Step)

**Prerequisites (User-Operated on Physical Phone + Host Terminal):**
1. Host daemon running Paseo `0.18.0` with `paseo-project-skills` installed/reloaded at the final M5.6 candidate commit.
2. Disposable Git fixture repo created (e.g. `repo-mobile-fixture` with `package.json` for React/TypeScript + 1 pre-existing `.agents/skills/debug-regression/SKILL.md` for conflict/observed testing).
3. Fixture repo temporarily enrolled via `scripts/enroll-project-skills.mjs enroll --root <fixture>` and `relay-policy --allow` enabled (strictly for the test window).

**Execution Checklist on Physical Paseo Mobile (iOS / Android):**
1. **Setup & Touch / Keyboard (`UX-5`, `CAT-5`):**
   - Open **Project Skills** on Paseo Mobile. Verify 3-step bar (`1. Setup`, `2. Skills`, `3. Preview & Apply`) renders with zero horizontal overflow and comfortable `>= 44×44` tap targets.
   - Tap `Choose project or workspace` → type in search input → verify soft keyboard opens without obscuring controls and closes cleanly on selection (or test `Advanced: Enter path manually` with `<fixture>`).
   - Toggle provider chips (`Codex`, `Kiro`) and tap `Select Detected Providers` / `Clear providers` → confirm responsive touch and no layout clipping.
2. **Scan, Search, Grouping & Scalability (`UX-1`, `UX-2`, `UX-5`, `UX-6`):**
   - Tap `Scan & Recommend` → verify Step 2 (`Skills`) loads pinned `v0.1.0 (4044fbf0)`.
   - Type in skill search (`go-api-change`) → verify `Unknown` auto-reveals, select it, clear search → verify hidden selected count banner appears → tap `Show Selected` → confirm smooth scrolling and keyboard dismissal.
   - Switch grouping (`By Applicability`, `By Boundary`, `By Observed Status`) → verify `Observed in project` label and non-activation disclaimer.
   - Tap `Select Recommended (+N)` → verify manual selection preserved; deselect conflicting `debug-regression` (after confirming Step 3 conflict banner) and keep 1 clean create skill (e.g. `implement-change`).
3. **Preview Preservation & Safe Apply (`UX-7`, `APP-3`):**
   - Navigate Step 2 → Step 3 → tap `Preview Changes` → verify distinct badges (`Create`, `Conflict`).
   - Navigate Step 3 → Step 1 → Step 2 → Step 3 → verify scroll resets to top on each step, hidden steps cannot be tapped, and Preview remains valid without re-running.
   - Complete two-step approval (`Review create-only approval` → `Confirm create-only`) on the clean create plan → record the displayed `operationId` and verify `completed` status.
4. **Force-Kill & Cold-Start Recovery (`OPS-1`, `OPS-4`):**
   - Completely force-kill Paseo Mobile from the OS app switcher.
   - Relaunch Paseo Mobile → open **Project Skills** → navigate to Step 3 (`Apply Operations`).
   - Verify the recorded `operationId` is automatically rediscovered via `apply.list.v1` and tapping `Operation ledger` lazily loads the created file rows.
5. **Background Suspend & Network Drop (`OPS-2`, `OPS-3`):**
   - Background Paseo Mobile for >60 s, then return → tap `Refresh operations` → verify clean state with zero duplicate rows.
   - Enable Airplane Mode (or disable Wi-Fi/cellular) → verify offline notice appears without crashing or losing UI stability → restore network → verify recovery without automatic Apply/retry.
6. **Live Relay Revocation & Manual Known-ID Lookup (`OPS-6`, `OPS-7`):**
   - On host terminal, run `scripts/enroll-project-skills.mjs relay-policy --deny` (do **not** restart daemon).
   - On Mobile, tap `Refresh operations` → verify immediate `unsupported_environment` policy notice and clearing of discovery-only rows.
   - Expand `Look up operation by ID`, paste the recorded `operationId`, tap `Check by ID` → verify authoritative status and full ledger still load via `apply.status.v1`.
7. **Teardown & Restoration:**
   - Revoke disposable fixture enrollment (`revoke --root <fixture>`), confirm `relay-policy --deny` (`allowRelay: false`), delete disposable fixture directory, and verify `paseo-slp-orchestrator` / `kanbanly` / `paseo-kiro-usage` remain `running`.
