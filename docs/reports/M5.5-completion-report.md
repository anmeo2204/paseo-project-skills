## 2. Implementation Summary (Decisions D1–D3 & Corrections P1–P5)

### Approved Decisions
- **D1 (Approach C):** Added `apply.list.v1` for trust-boundary-gated daemon operation discovery while preserving existing Desktop `localStorage` compatibility (`paseo-project-skills.apply-operations.v1`) and manual known-ID lookup via `apply.status.v1`. The daemon journal remains the single authoritative source of operation state.
- **D2 (Reuse daemon trust-boundary policy):** `apply.list.v1` calls `verifyTrust()` (`checkDaemonTrustBoundary(daemonHome, { env, allowRelay: readHostRelayOptIn(daemonHome) })`) on every request, reusing the exact existing host Relay opt-in policy (`enrollments.json` `allowRelay: true`).
- **D3 (Pagination bounds):** `applyListInputSchema` defaults `limit` to `20` and enforces `1 <= limit <= 50`.

### Required Corrections
- **P1 — Relay revocation:**
  - `index.server.ts` re-evaluates `verifyTrust()` on every `apply.list.v1` invocation (both when Apply is active and in the fallback `daemonHome` branch), returning `{ status: "error", code: "unsupported_environment" }` immediately upon Relay revocation without requiring a daemon restart.
  - On `unsupported_environment`, `FixtureOperations` calls `tracker.clearDiscoveryOnly(host.id, slot)`, clearing discovery-only cached entries while preserving locally submitted/checked operations and surfacing a clear notice.
  - Known-ID `apply.status.v1({ operationId })` remains readable for recovery when Relay is active without `allowRelay`.
  - No claim is made of per-device authorization or retroactive revocation of data already disclosed to a client before revocation.
- **P2 — Concurrent response freshness:**
  - `FixtureOperations` binds every `apply.list.v1` request to both the current `connection.current === binding` object (host, slot, online state, RPC handles) and a monotonic `listTokenRef` token. Delayed or out-of-order `apply.list.v1` replies from previous hosts (`A → B → A`), disconnects, or superseded refreshes are discarded.
  - `client/apply-tracker.ts` uses monotonic `phaseRanks` (`accepted < preflight < writing < completed/failed_before_write/partial_failure/recovery_required`) in `ingestDiscovered()` so delayed discovery summaries can never overwrite a fresher authoritative `ApplyOperation` from `apply.status.v1` or regress a terminal phase.
- **P3 — Bounded & safe journal discovery:**
  - `ApplyJournal.list()` is strictly read-only: it reuses `checkDirectory()` (owner UID, `0o700`, non-symlink canonical path) and `readEntryReadOnly()` (`O_RDONLY | O_NOFOLLOW | O_NONBLOCK`, regular file, `nlink === 1`, owner UID, `0o600`), never unlinks, writes, fsyncs, or prunes any journal record.
  - Missing files from concurrent deletion (`ENOENT`) are skipped cleanly; unreadable/corrupted/wrong-mode/symlink files increment `unreadableCount` (surfaced as a warning banner in `FixtureOperations`) without failing discovery of valid records.
  - Bounded caps enforced via `journalListLimits`: `maxDirectoryEntries = 256`, `maxRecordReads = 64`, `maxTotalReadBytes = 16 MiB`, `maxScanDurationMs = 2000`, `maxResponseBytes = 256 KiB`.
  - Priority sorting places `recovery_required`, `partial_failure`, and active phases (`accepted`, `preflight`, `writing`) in priority bucket `0` ahead of `completed` / `failed_before_write` in bucket `1`, ordered deterministically by `(priority ASC, updatedAt DESC, operationId ASC)` with keyset cursor `^[01]:[0-9]{1,16}:[a-f0-9]{32,64}$` to prevent duplicates across pages.
  - `applyOperationSummarySchema` exposes only `{ operationId, planDigest, phase, code, targetMutated, requiresPreview, ledgerCount, createdAt, updatedAt }` — zero filesystem paths, zero ledger rows, zero `requestHash`/`receiptHash`, and zero source bytes.
- **P4 — Preserve M4 submission tracking:**
  - `tracker.submit()` retains synchronous tracking-before-submit and fails closed with `tracking_unavailable` if `localStorage` throws, without invoking `apply.create.v1`.
  - Existing `localStorage` key and entry format remain unchanged; discovered summaries are held in-memory (`discovered: true`) and never written to `localStorage` unless explicitly checked/submitted.
  - UI copy and documentation avoid absolute crash-proof claims: recovery is bounded by daemon journal persistence, retention rules, and trust-boundary access.
- **P5 — Retention & reconciliation:**
  - Existing `ApplyJournal` retention policies are untouched.
  - Absence of an operation from a discovery page never implies completion or deletion; `truncated: true` surfaces an explicit notice to the user.
  - `clearDiscoveryOnly()` only clears `discovered: true` entries without a local `operation` and never silently discards unresolved or `recovery_required` tracked operations.
  - No automatic cleanup, retry, resume, rollback, or Apply is performed.

## 3. Security Analysis

1. **No caller principal assumption:** Paseo SDK `0.17.4` does not expose per-client caller identity to plugin RPCs. Accordingly, `apply.list.v1` is gated solely by the daemon's existing host trust boundary (`checkDaemonTrustBoundary` + explicit host CLI `allowRelay` opt-in).
2. **Live Relay revocation:** Because `verifyTrust()` reads `config.json` and `enrollments.json` on every `apply.list.v1` call, revoking `allowRelay` takes effect immediately on the next request without restarting the daemon. Previously disclosed data already held in a client's memory cannot be retroactively revoked; `clearDiscoveryOnly()` removes cached discovery-only rows on the next denied refresh.
3. **Minimal metadata exposure:** Discovery responses omit target directory paths, ledger destination paths, `requestHash`/`receiptHash`, and file contents. Full ledger rows are loaded lazily on demand via `apply.status.v1({ operationId })` only when the user expands `Operation ledger`.
4. **Read-only filesystem hardening:** `ApplyJournal.list()` enforces directory ownership/mode/canonicality, refuses symlinks/hardlinks/wrong-mode files via `O_NOFOLLOW` + `fstat`, and enforces strict entry/read/byte/time/response caps to prevent DoS against the daemon.

## 6. Remaining Limitations

- **Physical Mobile acceptance deferred to M5.6:** Real iOS/Android force-kill, background suspend, and network-drop reconnect acceptance on physical Mobile devices remains deferred to M5.6 Production Acceptance (this milestone verified emulated `390×844` cold-start recovery with cleared storage).
- **Durability bounds:** Operation tracking is bounded by daemon journal durability and existing retention policies (expired terminal records are pruned per M4 rules); it is not claimed to be universally crash-proof across disk loss or manual journal deletion.
- **No per-device authorization or retroactive revocation:** Because Paseo SDK `0.17.4` has no caller principal, discovery authorization is host-wide under the daemon trust boundary, and revoking Relay opt-in prevents future discovery calls without retroactively erasing data already rendered on a client.
