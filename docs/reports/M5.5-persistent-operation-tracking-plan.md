## 2. Root Cause of Mobile Persistence Limitations

1. **Absence of `localStorage` on React Native:** On Paseo Mobile, `globalThis.localStorage` is undefined, causing `resolveClientProfileStorage()` to fall back to ephemeral `createMemoryStorage()`. Force-killing or reloading the Mobile app erases all client-side `operationId` references.
2. **No General Client Storage API in Paseo SDK `0.17.4`:** `@getpaseo/plugin/client` does not expose `AsyncStorage`, `MMKV`, or `IndexedDB` for plugin screens; its only durable screen persistence primitive is `defineSettings({ scope: "host" | "device" })`.
3. **No Daemon Operation Discovery:** While `ApplyJournal` already persists every admitted operation durably on the daemon host and `apply.status.v1({ operationId })` can read it anytime, the client has no safe way to rediscover `operationId`s after losing local memory.

## 3. Comparison of Approaches A, B, and C

| Dimension | Approach A: Client-Side Durable Storage (`scope: "device"` settings) | Approach B: Host-Scoped Paseo Settings (`scope: "host"` operation refs) | Approach C: Trust-Boundary-Gated Daemon Discovery RPC (`apply.list.v1`) |
| --- | --- | --- | --- |
| **Mobile restart / force-kill recovery** | Survives restart if `scope: "device"` is supported on Mobile, **but** loses operation if app crashes between `apply.create.v1` and async save. | Survives restart across Desktop & Mobile, **but** requires async write-before-submit (latency + conflict retry) and misses non-UI submissions. | **100% crash-proof:** `ApplyJournal` is written atomically + `fsync` before any target mutation. |
| **Desktop & Mobile consistency** | Device-local only; operations started on Desktop are invisible on Mobile and vice versa. | Consistent across Desktop & Mobile paired to the same host. | **Consistent across Desktop & Mobile** directly from the authoritative daemon journal. |
| **Host isolation** | Must manually filter by `hostId` inside shared device settings. | Inherently scoped to `host` by Paseo daemon. | **Inherently scoped to `hostId` + `installation`** verified on the daemon. |
| **Concurrent clients** | No contention across devices, but blind to other clients' active/recovery operations. | Requires serialized/coalesced writes + optimistic concurrency conflict retries across clients. | **Zero write contention:** strictly read-only on daemon journal. |
| **Relay / Security without caller principal** | Strongest Relay isolation (no daemon enumeration), **but** `scope: "device"` is unverified on Paseo `0.18.0` Mobile runtime. | **Weaker Relay boundary:** Paseo's built-in `settings` RPC exposes `scope: "host"` settings over Relay even when `allowRelay: false`! | **Explicitly trust-boundary gated:** `apply.list.v1` enforces `checkDaemonTrustBoundary` (fails closed over Relay when `allowRelay: false`), never exposes paths or ledger rows in list summaries. |
| **Corrupted / inaccessible journals** | Client holds stale refs; `apply.status.v1` returns `outcome_unknown`. | Client holds stale refs; `apply.status.v1` returns `outcome_unknown`. | Daemon skips/counts corrupted individual files (`unreadableCount`) without hiding valid recovery records; fails closed (`journal_unavailable`) if directory identity is unsafe. |
| **Authoritative state** | Client tracks refs; daemon authoritative via `apply.status.v1`. | Client/host settings track refs; daemon authoritative via `apply.status.v1`. | **Single source of truth:** daemon journal is both discovery index and authoritative state. |

## 4. Recommended Architecture and Justification

### Recommended: **Trust-Boundary-Gated Daemon Discovery (`apply.list.v1`, Approach C) + Existing `localStorage` Migration + Manual `Operation ID` Recovery Lookup**

1. **Authoritative & Minimal:** Reuses the existing `ApplyJournal` (`max 64` records) with one strictly read-only, bounded, paginated RPC (`apply.list.v1`) returning **summary metadata only** (no paths, no ledger rows).
2. **Superior Relay Security vs Approach B:** Unlike `scope: "host"` settings (which Paseo exposes over Relay regardless of `allowRelay`), `apply.list.v1` explicitly enforces `checkDaemonTrustBoundary(daemonHome, { allowRelay: readHostRelayOptIn(daemonHome) })` — failing closed over Relay unless the single-owner host explicitly opted in via `enroll-project-skills.mjs relay-policy --allow`.
3. **Zero Write-Before-Submit Races:** Eliminates async client settings writes before `apply.create.v1` and eliminates orphaned/stale client reference lists.
4. **Full Compatibility & Fallback When Relay Opt-In Is Revoked:**
   - Desktop retains `localStorage` restoration (migrating/merging smoothly with `apply.list.v1` deduplicated by `operationId`).
   - Even if `relay-policy --deny` is later toggled (blocking `apply.list.v1`), **both** existing `apply.status.v1({ operationId })` AND a compact **Look up operation by ID** control remain available so a user with a recorded `operationId` can always inspect recovery status!
   - Never mutates journal state (never prunes/unlinks during `list()`), never auto-retries, never auto-resumes, never auto-rolls back, and never authorizes Apply.

## 5. Trust-Boundary and Security Analysis

### 5.1 Absence of Caller Principal in Paseo SDK `0.17.4` / Paseo `0.18.0`
- Paseo SDK `0.17.4` RPC handlers receive `{ paseo }` without a cryptographic caller principal or per-device identity.
- Consequently, any RPC registered on the daemon is reachable by any client connected to that daemon (loopback Desktop, or paired Mobile devices when Relay is enabled).

### 5.2 Trust Boundary & Authorization for `apply.list.v1`
- **Strict Fail-Closed Gate:** `apply.list.v1` executes **only** when `checkDaemonTrustBoundary(daemonHome, { env, allowRelay: readHostRelayOptIn(daemonHome) }).ok === true`:
  - **Local loopback (`relay.enabled: false`, loopback `listen`, `remote.enabled: false`):** Allowed.
  - **Relay ON with `allowRelay: false` (default):** **Denied** (`{ status: "error", code: "unsupported_environment" }`) — prevents unrestricted journal enumeration over Relay.
  - **Relay ON with explicit host CLI `relay-policy --allow` (single-owner personal host):** Allowed within the documented single-owner paired-device trust boundary (the same boundary required for Mobile Apply).
- **Host & Installation Scoping:** Only journal files where `record.hostId === self.serverId && record.installation === mainPluginInstallationId` are returned.
- **Data Minimization in `apply.list.v1`:**
  - **Included (`ApplyOperationSummary`):** `operationId`, `planDigest`, `phase`, `code`, `targetMutated`, `requiresPreview`, `durability`, `ledgerCount`, `updatedAt`.
  - **Explicitly Excluded from `apply.list.v1`:** Target directory paths, file/directory `destination` paths, full `ledger` rows, `requestHash`, `receiptHash`, `instance`, and source bytes.
  - Full `ledger` rows are fetched **only on demand** via existing `apply.status.v1({ operationId })` when the user expands or checks a specific operation.
- **Read-Only Journal Invariant:** `ApplyJournal.list()` performs **zero** filesystem mutations (`unlinkSync`, `renameSync`, `writeFileSync`, `fsyncSync` are never called during discovery). Expired terminal records are simply filtered out of the response; actual pruning remains strictly inside `checkAdmission()` under the native writer's daemon-wide lease.
- **Non-Authorization:** Discovered `operationId` / `planDigest` summaries are purely observational and can never be replayed to authorize or trigger `apply.create.v1`.

## 6. Operation Discovery and Recovery Lifecycle

### 6.1 Proposed Wire Contract (`shared/apply.ts`)
```ts
export const applyListInputSchema = z.strictObject({
  limit: z.number().int().min(1).max(50).optional(), // default 20
  cursor: z.string().regex(/^[0-9]{1,16}:[a-f0-9]{32,64}$/).optional(),
});

export const applyOperationSummarySchema = z.strictObject({
  operationId: operationIdSchema,
  planDigest: digest,
  phase: applyOperationSchema.shape.phase,
  code: z.string().min(1).max(64),
  targetMutated: applyOperationSchema.shape.targetMutated,
  requiresPreview: z.boolean(),
  durability: applyOperationSchema.shape.durability,
  ledgerCount: z.number().int().nonnegative(),
  updatedAt: z.number().int().nonnegative(),
});

export const applyListOutputSchema = z.discriminatedUnion("status", [
  z.strictObject({
    status: z.literal("ready"),
    items: z.array(applyOperationSummarySchema).max(50),
    nextCursor: z.string().optional(),
    unreadableCount: z.number().int().nonnegative(),
  }),
  z.strictObject({
    status: z.literal("error"),
    code: z.enum(["invalid_request", "journal_unavailable", "unsupported_environment"]),
  }),
]);
```

### 6.2 Discovery, Merge & Lifecycle Rules
1. **Startup / Reconnect / Host Switch:**
   - `FixtureOperations` restores any Desktop `localStorage` entries (`tracker.restore()`), then calls `apply.list.v1({ limit: 20 })` when `online === true`.
   - Monotonic connection/binding token rejects delayed `apply.list.v1` replies after disconnect, host switch, or unmount.
2. **Merging into `createOperationTracker`:**
   - Add `tracker.ingestDiscovered(hostId, slot, items)` (strictly in-memory merge, does not break existing `submit` / `check` / `offline` / `localStorage` format!):
     - Existing entries with a richer full `ApplyOperation` (including `ledger`) are preserved unless the discovered `phase` has advanced to a terminal/recovery phase.
     - Newly discovered operations (e.g., after Mobile force-kill or from another device) are inserted with their authoritative summary (`phase`, `code`, `targetMutated`, `requiresPreview`, `durability`) and `ledgerLoaded: false`.
     - Pending (`accepted` / `preflight` / `writing`) operations from a previous daemon instance are reported by the daemon as `recovery_required` (`terminal_record_missing`) without mutating the journal file.
3. **On-Demand Ledger Fetch:**
   - Clicking **Operation ledger** or **Check operation status** calls existing `apply.status.v1({ operationId })` to load the full `ledger` rows on demand.
4. **Corrupted / Missing / Inaccessible Journals:**
   - Missing coordinator directory (host never ran Apply): returns `{ status: "ready", items: [], unreadableCount: 0 }`.
   - Coordinator directory fails safety checks (`uid`, `0700`, `realpath`, symlink): fails closed with `{ status: "error", code: "journal_unavailable" }`.
   - Individual corrupted/oversized/wrong-mode JSON file: skipped and counted in `unreadableCount` (UI shows a non-blocking warning: *"N journal record(s) could not be read; inspect `~/.paseo/runtime/project-skills/coordinator/` on the host."*), so valid recovery records remain discoverable!
5. **Migration from Current Client-Side Storage:**
   - Zero breaking change to `project-skills.apply-operations.v1:<slot>` in Desktop `localStorage`. Existing Desktop entries continue to restore and check via `apply.status.v1`, and deduplicate seamlessly against `apply.list.v1` by `operationId`.

## 10. Decisions Requiring Explicit User Approval

1. **Recommended Architecture (Approach C-Gated vs Approach A/B):**
   - **Recommended:** Trust-boundary-gated daemon discovery RPC (`apply.list.v1`) returning compact path-free summaries + existing Desktop `localStorage` migration + collapsible `Look up operation by ID` fallback (`apply.status.v1`).
   - **Alternative 1 (Approach B):** Host-scoped Paseo settings (`scope: "host"`) storing `{ operationId, planDigest }` references (note: exposed over Relay even when `allowRelay: false` and has write-before-submit race).
   - **Alternative 2 (Approach A):** Device-scoped Paseo settings (`scope: "device"`) (note: no cross-device consistency and requires runtime verification of `scope: "device"` on Paseo Mobile).
2. **Relay Policy for `apply.list.v1`:**
   - **Recommended:** Gate `apply.list.v1` by the exact same `checkDaemonTrustBoundary` check as Apply (allowed on local loopback or when `relay-policy --allow` is explicitly enabled; fail closed with `unsupported_environment` over Relay when `allowRelay: false`), while keeping `apply.status.v1({ operationId })` readable for manual recovery even after `relay-policy --deny`.
   - **Alternative:** Restrict `apply.list.v1` to local loopback only (never allowed over Relay even with `relay-policy --allow`), which would require pairing with Approach A/B for Mobile over Relay.
3. **Pagination & Summary Limits:**
   - **Recommended:** Default `20` items per page (max `50`, matching `ApplyJournal`'s hard `64`-record ceiling), returning summary metadata only (no paths, no ledger rows) with lazy ledger fetch via `apply.status.v1`.
   - **Alternative:** Different default page size (e.g., `10` or `64`).

Please review and confirm these decisions before I begin M5.5 implementation.
